# ODIGA (오디가)

### 자연어 검색과 혼잡도 정보를 활용한 맞춤형 장소·코스 추천 서비스

약속을 잡을 때 가장 오래 걸리는 일 중 하나는 어디에서 무엇을 할지 결정하는 것입니다. 원하는 지역을 정하더라도 장소를 하나씩 찾아보고, 이동 거리와 분위기, 방문 시간까지 고려하다 보면 생각보다 많은 시간이 필요합니다.

**오디가(ODIGA)** 는 이런 과정을 조금 더 편리하게 만들기 위해 개발한 장소 및 코스 추천 서비스입니다.

사용자가 원하는 지역, 시간, 활동을 자연어로 입력하면 검색 조건을 분석하고, 장소 정보와 혼잡도 데이터를 활용해 방문 코스를 추천합니다. 추천받은 장소를 지도에서 확인하고, 원하는 대로 코스를 수정하거나 공유할 수 있도록 구성했습니다.

## 프로젝트 소개

오디가는 단순한 장소 검색보다 **사용자의 상황에 맞는 코스 추천**에 초점을 맞췄습니다.

예를 들어 다음과 같은 문장을 입력할 수 있습니다.

> 성수에서 오늘 저녁 7시에 칵테일바 가고 싶어.

사용자가 검색 조건을 하나씩 선택하지 않아도 문장에서 지역, 시간, 장소 유형 등을 추출하도록 구현했습니다.

검색 요청은 Spring Boot 서버로 전달되며, Gemini API를 통해 조건을 분석합니다. 이후 장소 후보를 선정하고, 사용자의 요청과 장소별 특성을 고려하여 추천 결과를 구성합니다.

### 주요 기능

| 기능 | 설명 |

| 맞춤형 장소 추천 | 검색 조건과 장소 정보를 반영해 추천 결과 생성 |

## 사용 흐름

### 1. 자연어로 장소 검색

오디가는 사용자가 입력한 문장에서 필요한 정보를 추출합니다.

검색 예시:

> 토요일 오후 3시에 홍대에서 조용한 데이트 코스 추천해 줘.

이 문장에서는 홍대라는 지역, 토요일 오후 3시라는 방문 시간, 조용한 분위기와 데이트 목적을 검색 조건으로 활용할 수 있습니다.

Gemini API 연결이 어려운 상황을 고려해 규칙 기반 조건 추출 방식도 함께 구현했습니다.

### 2. 추천 장소 및 코스 확인

추출된 조건을 바탕으로 장소 후보를 선정하고 추천 코스를 생성합니다.

추천 과정에서는 요청한 지역과 장소 유형뿐 아니라 장소별 태그, 사용자 선호, 활용 가능한 혼잡도 정보 등을 고려합니다.

사용자는 추천 결과를 확인하면서 방문하고 싶은 장소를 선택할 수 있습니다.

### 3. 지도와 혼잡도 확인

지도 화면은 Flutter의 `flutter_map`과 OpenStreetMap을 사용했습니다.

추천된 장소의 위치를 확인할 수 있으며, 혼잡도 데이터를 이용해 지역별 혼잡 수준을 표시하도록 구성했습니다.

혼잡도 데이터는 지역과 시간에 따라 달라지므로 사용자가 방문할 시간을 고려해 장소를 선택할 수 있도록 하는 것이 목표입니다.

### 4. 코스 수정

추천된 코스를 그대로 사용하는 것뿐 아니라 사용자가 원하는 형태로 수정할 수 있도록 구성했습니다.

마음에 들지 않는 장소를 제외하거나 다른 장소를 추가하고, 방문 순서를 변경하는 방식으로 코스를 조정할 수 있습니다.

### 5. 공유 및 개인 설정

사용자가 만든 코스를 다른 사람과 공유할 수 있도록 관련 API와 데이터 모델을 설계했습니다.

사용자 정보와 선호 설정은 MySQL을 사용하는 영역입니다. 공유 정보의 영구 저장과 서버 재시작 이후 재조회 기능은 실제 DB 연결 상태에 따라 검증이 필요합니다.

## 시스템 구조

프론트엔드는 Flutter Web, 백엔드는 Spring Boot를 사용했습니다.

사용자가 앱에서 검색하면 서버가 요청을 받아 검색 조건을 추출하고, 장소 정보와 추천 로직을 활용하여 결과를 반환하는 구조입니다.

### 혼잡도 데이터 처리

혼잡도 분석을 위해 Python으로 데이터를 전처리했습니다.

LG 원본 데이터는 GitHub에 업로드하지 않고 시연 노트북의 로컬 환경에 보관합니다.

로컬 백엔드에서 `ODIGA_DATA_DIR`을 지정하면 전처리한 LG 데이터 파일을 읽도록 구성했습니다. 별도 경로를 지정하지 않으면 기본 혼잡도 파일을 사용합니다.

따라서 로컬 실행 환경과 배포 환경에서 활용하는 혼잡도 데이터는 서로 다를 수 있습니다.

## 추천 알고리즘 평가

추천 결과가 검색 조건에 얼마나 적합한지 확인하기 위해 랜덤 추천, 인기순 추천, 거리순 추천 방식과 오디가 추천 방식을 비교했습니다.

평가는 성수, 홍대, 강남의 9개 검색 시나리오를 대상으로 진행했으며, Precision@5와 nDCG@5 지표를 사용했습니다.

- **Precision@5:** 상위 5개 추천 결과 중 평가 기준에 부합하는 장소의 비율
- **nDCG@5:** 추천 결과의 적합성과 순위를 함께 고려한 값

## 로컬 실행 방법

오디가는 Spring Boot 서버와 Flutter 앱을 각각 실행하는 방식으로 시연할 수 있습니다.

### 실행 환경

| 항목 | 환경 |
|---|---|
| Java | JDK 21 |
| Flutter | Flutter SDK |
| 브라우저 | Chrome |
| 데이터베이스 | MySQL |
| 개발 도구 | IntelliJ IDEA, VS Code |
| 운영체제 | Windows, macOS 등 |

### 1. 프로젝트 다운로드

```bash
git clone https://github.com/shiwjz/lzu-capstone.git
cd lzu-capstone
```

### 2. 환경변수 설정

백엔드 실행 전에 DB 및 외부 API 설정이 필요합니다.

주요 환경변수는 다음과 같습니다.

```env
GEMINI_API_KEY=
GOOGLE_PLACES_API_KEY=
DB_URL=
DB_USERNAME=
DB_PASSWORD=
JWT_SECRET=
ODIGA_DATA_DIR=
```

실제 API 키와 비밀번호는 GitHub에 업로드하지 않습니다.

Spring Boot는 루트 폴더의 `.env` 파일을 자동으로 읽지 않으므로 실행 환경에서 별도로 환경변수를 설정해야 합니다.

### 3. 백엔드 실행

Windows PowerShell 기준:

```powershell
cd capstone-backend
.\gradlew.bat bootRun
```

macOS 또는 Linux:

```bash
cd capstone-backend
./gradlew bootRun
```

서버가 정상적으로 실행되면 다음 주소에서 응답을 확인할 수 있습니다.

`http://localhost:8080/api/test`

### 4. Flutter 앱 실행

백엔드를 실행한 상태에서 새로운 터미널을 열어 Flutter 앱을 실행합니다.

```bash
cd capstone_odiga
flutter pub get
flutter run -d chrome --dart-define=ODIGA_API=http://localhost:8080
```

`ODIGA_API`는 Flutter 앱에서 호출할 백엔드 주소입니다.

이 옵션을 지정하지 않으면 프로젝트의 설정에 따라 Mock API가 사용될 수 있으므로 실제 서버 연동을 확인할 때는 주소를 명시해야 합니다.

특정 상호명 매칭은 실제 검색 결과에 따라 달라질 수 있으므로 시연 전에 정확도를 확인해야 합니다.

사용자가 요청한 분위기와 방문 시간을 바탕으로 추천 결과를 확인합니다.

MySQL 연결 상태, Gemini API 설정, Google Places API 응답과 장소 사진 표시 여부도 함께 점검합니다.

로컬 LG 데이터를 사용하는 경우 `ODIGA_DATA_DIR` 경로와 전처리 파일의 존재 여부를 확인합니다.

## 데이터베이스 설계

MySQL을 이용해 사용자 정보와 서비스 관련 데이터를 관리하도록 설계했습니다.

ERD는 기능 개발 과정에서 여러 차례 수정했으며, v3에서는 코스 공유 및 장소 저장 기능을 위한 구조를 정리했습니다.

주요 테이블은 다음과 같습니다.

| 테이블 | 용도 |
|---|---|
| `users` | 사용자 정보 |
| `user_preference` | 사용자 선호 설정 |
| `user_allergy` | 사용자 알레르기 정보 |
| `place` | 장소 기본 정보 |
| `place_tag` | 장소 관련 태그 |
| `course` | 추천 코스 및 검색 조건 |
| `course_place` | 코스에 포함된 장소 |
| `course_share` | 코스 공유 정보 |
| `saved_place` | 사용자가 저장한 장소 |

ERD 설계 파일은 `database/erd/`에서 확인할 수 있습니다.

설계 파일과 실제 데이터베이스는 별도로 관리되므로, 테이블 구조가 반영되었는지는 SQL과 MySQL 연결을 통해 확인해야 합니다.

## 개발하면서 확인한 점

### 자연어 조건 추출과 실제 추천 결과는 구분해서 봐야 했습니다.

Gemini API가 검색 문장에서 지역과 시간, 장소 유형을 올바르게 추출하더라도 실제 추천 결과가 사용자의 의도와 정확히 일치하는 것은 아니었습니다.

검색 조건 분석뿐 아니라 장소 후보를 선정하고 점수를 계산하는 과정도 중요하다는 점을 확인했습니다.

### 혼잡도 데이터는 실행 환경에 영향을 받습니다.

LG 원본 데이터는 로컬에서 관리하기 때문에 다른 개발 환경이나 배포 서버에서 동일한 데이터가 자동으로 사용되지는 않습니다.

전처리 파일의 위치와 설정을 관리하고, 데이터가 없는 경우 기본 혼잡도 파일을 사용하는 방식을 마련했습니다.

### 외부 API와 DB 연결 상태도 시연 결과에 영향을 줍니다.

Gemini와 Google Places는 외부 API이기 때문에 네트워크 환경이나 사용량 제한에 따라 요청이 실패할 수 있습니다.

MySQL 역시 서버 상태와 접속 정보에 영향을 받으므로 발표 전 정상 동작 여부를 확인해야 합니다.

이러한 문제를 고려해 로컬 실행 방법과 시연 점검 사항을 정리했습니다.
